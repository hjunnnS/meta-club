# G1 클럽 웹 앱

Node.js 24 이상에서 실행한다. 같은 공개 HTTPS 주소로 PC·모바일 웹을 제공하고, TLS 프록시가 원래 Host와 X-Forwarded-Proto: https를 로컬 서버로 전달하도록 설정한다.

Google에는 웹 OAuth 클라이언트와 `/auth/callback/google`의 전체 HTTPS 주소를 등록한다. Apple에는 Sign in with Apple이 연결된 Services ID, 도메인, `/auth/callback/apple`의 전체 HTTPS Return URL을 등록한다. AUTH_APPLE_SECRET에는 해당 Services ID용으로 서명된 유효한 client secret JWT를 넣고 만료 전에 갱신한다. AUTH_SECRET에는 충분히 긴 무작위 값을 설정한다.

이 디렉터리에서 `npm ci` 후 .env.example을 참고해 .env를 작성하고 `node --env-file=.env server.js`로 실행한다. 이미 서버 환경 변수를 주입했다면 `npm start`를 사용한다. 계정은 인증 제공자와 제공자의 고유 사용자 ID 조합으로 식별한다.

## 게스트 접근 권한

D-05에 따라 로그인 전에도 로비 열람과 클럽 입장이 가능하다. `GET /api/access`는 현재 사용자의 유형과 이 두 접근 권한을 반환한다. `/api/account`는 인증된 계정에만 제공한다. 클럽 입장 권한은 좌석이나 정원을 예약하지 않는다.

클럽 내부에서 게스트가 사용할 세부 활동은 추후 결정한다. 후속 기능은 입장 권한을 개별 활동 권한으로 재사용하지 않고 해당 정책을 서버에서 별도로 적용한다.

## 세션 유지와 만료 (#15)

새로고침해도 서버는 기존 Auth.js 쿠키를 복호화해 같은 계정을 복원한다. `GET /api/session`은 인증 시 사용자 ID와 현재 쿠키의 만료 시각을, 게스트면 사유를 반환한다. 계정 API의 거절 응답은 HTTP 401이며 사유는 쿠키 없음(`login_required`), 만료된 쿠키 재사용(`session_expired`), 복호화·검증 실패(`session_invalid`)로 구분한다. 브라우저가 만료 쿠키를 이미 제거했다면 서버에는 쿠키 없음으로 표시된다.

세션 수명과 정상 세션의 갱신은 기존 Auth.js 설정을 따른다. 상태 조회 자체는 만료 시각을 연장하지 않는다. 세션 만료 후에도 게스트의 로비 열람·클럽 입장 권한은 적용된다.

## 운영자 접근 (#24)

운영자는 일반 사용자와 같은 Google·Apple 로그인으로 인증한다. 서버의 `OPERATOR_ACCOUNT_IDS`에 승인한 계정의 `/api/account` 응답 ID를 쉼표로 구분해 등록한다. 예를 들어 Google 계정의 형식은 `google:<provider subject>`다. 빈 설정은 모든 계정의 운영 접근을 거절한다. 목록을 바꾼 뒤 서버를 재시작하면 기존 로그인에도 변경 사항이 적용된다.

운영자 계정에는 홈에 운영자 공간 링크가 표시된다. 서버는 `/operator`와 `/api/operator` 아래의 요청마다 세션과 목록을 확인한다. 미인증·만료는 401, 인증된 일반 계정은 403이다. 거절 시 서버 표준 오류 로그에 `operator_access_denied` JSON 한 줄을 남긴다. 로그에는 시각·접근 영역·메서드·확인된 계정 ID·상태 코드·거절 사유를 기록한다.

## EDM 채널 입장 (#30·#33)

홈의 **클럽 로비**에서 EDM을 선택하면 같은 서버의 채널에 연결한다. Google·Apple 회원은 기존 계정 ID, 게스트는 서버가 서명한 브라우저 쿠키로 구분한다. 빈자리가 있는 EDM 채널을 우선 배정하고 모두 차면 새 채널을 생성한다. 현재 데스크톱 기준은 채널당 사람 60명이다. 좌석 예약은 15초간 유효하며 실제 WebSocket 입장이 완료된 클라이언트만 인원에 포함한다. AI는 사람 좌석을 예약하지 않는다. 입퇴장 때마다 같은 채널의 관측 화면에 서버 실인원을 전송한다.

단일 앱 프로세스에서 채널을 관리한다. TLS 프록시가 같은 호스트의 WebSocket 업그레이드와 Origin을 전달해야 한다. 맵 표시에는 저장소의 dance 디렉터리에서 설치한 Babylon.js 의존성이 필요하다(`npm ci --prefix dance`를 저장소 최상위에서 실행).

## 로비와 EDM

로비는 네 클럽의 상태를 표시한다. 검수가 끝난 EDM 인테리어에서 채널을 선택하거나 자동 배정받을 수 있다. 다른 세 클럽은 각 맵의 검수 이후 개방한다. 로비에서 닉네임과 기본 아바타를 저장하면 다음 입장에 반영된다. 현재 EDM에서 사용 중인 시험 모델을 G1 기본 아바타로 사용한다. 닉네임과 세 가지 색상 선택을 유지하며 모델은 이후 교체할 수 있다. 기기별 표현 예산은 별도로 검수한다.

채널의 서버 시계는 사람의 위치·방향·동작과 최대 20명의 AI 상태를 공유한다. 기본 AI 5명과 추가 댄서 최대 15명으로 구성하며 CLUB_AI_EXTRA_WHEN_EMPTY로 추가 인원을 낮출 수 있다. 빈 사람 자리 범위에서만 추가하며 만석이면 다시 5명이 된다. 바·라운지의 빈 좌석에 가까이 가서 착석하고 다시 누르면 일어선다. 게스트의 세부 활동은 정책 확정 전까지 잠겨 있다. 연결이 끊어지면 세션을 확인하고 최대 60초 동안 기존 채널 복귀를 시도한다. 채널이 사라졌거나 만석이면 새 배정의 입구에서 시작한다.

운영자 화면에서 채널의 사람·AI 수를 확인한다. 기존 신고와 운영 조치 기록은 읽기 전용으로 조회한다. 배포 시 CLUB_DB가 가리키는 파일과 상위 디렉터리를 영구 저장소에 둔다.

## EDM 음원 등록

운영자가 확보한 WAV와 승인 기록을 서버에 두고 CLUB_MUSIC_CATALOG에 JSON 배열 파일의 경로를 지정한다. 각 항목에는 id, title, club(edm), status(approved), approvedBy, evidence(계약·허가 기록 참조), webStreaming(true), territories(허용 지역 배열), from·until(시작·종료 시각), duration(초), file(목록 기준 상대 경로)이 필요하다. CLUB_TERRITORY는 운영 환경에서 실제로 서비스하는 지역과 일치해야 한다. 지역별 접속 제한이 필요한 계약은 배포 측에서 지역 제한이 보장된 경우에만 등록한다. 등록 후 재시작하면 승인 조건을 충족한 곡만 채널 목록에 포함한다. 재생 중에도 만료 시각을 확인한다.

서비스 시작 전에는 자체 제작한 음원을 위 승인 목록에 등록한다. 이 저장소에는 운영 음원이 없다. 권리 증빙이나 승인 목록이 비어 있으면 사용자가 음악 시작을 눌렀을 때 대기 사유를 표시한다.

## 외부 로그인 설정 전 G1 실행

로컬 HTTPS 프록시와 AUTH_SECRET을 설정하고 AUTH_URL을 해당 localhost HTTPS 주소로 지정한다. CLUB_LOCAL_TEST=1로 실행하면 Google·Apple 키 없이 홈에서 **시험 회원으로 입장**을 선택할 수 있다. Auth.js 화면의 G1 시험 회원 버튼을 누르면 고정 일반 계정으로 로그인한다. 로그아웃 후 같은 계정으로 돌아오면 저장한 프로필을 다시 사용한다. 독립적인 데이터를 쓰려면 CLUB_DB에 시험 전용 SQLite 경로를 지정한다.

이 모드에서 EDM의 **음악 시작**은 G0에서 사용한 12초 합성 시험 루프를 재생한다. 시험 음원은 외부 샘플 없이 220Hz 신호로 만든 WAV다. 공개 배포는 시험 모드를 끄고 Google·Apple 실제 로그인 및 자체 제작곡을 연결한다. 시험 세션은 공개 환경에서 사용할 수 없으며 시험 모드는 production이나 외부 도메인에서 시작되지 않는다.

## G2 EDM 시험 상품

로컬 시험 회원으로 EDM 채널에 입장한 뒤 **EDM 상품**을 연다. 축하 LED 메시지는 시험 가격 1,000원, 구매 채널에서 1회 15초다. 금지 문구는 기존 CHAT_BLOCKED_TERMS 설정을 공유한다. 미리보기는 본인 화면의 무대 전광판에만 표시되고 15초 뒤 또는 종료 버튼으로 원래 시점으로 돌아온다.

모의 구매 요청은 계정과 구매 의도별로 SQLite에 한 건을 저장한다. 같은 탭에서 창을 다시 열거나 새로고침해도 같은 채널에서는 진행하던 주문을 조회한다. 주문을 취소하거나 거절한 후 새 주문을 시작할 수 있다. 모의 승인 요청은 서버 검증 대기 상태까지만 기록한다. 후속 #31에서 결제를 검증하고 #34에서 이용권을 지급한다. 실결제 연결은 없다.
